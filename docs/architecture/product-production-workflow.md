# 产品生产模式主线记录

## 记录目的

这份文档记录 Yotsuba Ink 当前采用的产品生产模式，并作为后续持续更新的主线。

它不是单次需求清单，而是一套可复用的完整工作流：从产品定位、需求分析、技术选型、UI 设计、前端开发、后端开发、双端协调、测试，到运维部署和持续迭代。每次产品阶段推进、主线决策变化、前后端接口合同变化，都应更新这里。

## 当前阶段

当前处于 **后端真实 API 接入与链路稳定化阶段**。

前端 mock 验收已经基本收口，本阶段目标是把已成型的三档模式、阶段合同、SSE 事件、人工 checkpoint、写回面板和导出留页逻辑接入真实后端编排与真实 OpenAI-compatible API。

当前重要约束：

- 生产链路不再走前端 mock 或后端 mock provider；所有创作阶段默认调用真实 OpenAI-compatible provider。
- 三档模式语义先稳定，再对接后端：极速生产、平衡创作、精细定稿。
- 前端页面不靠堆 card 填空间，必须先定义阶段产物、用户决策、写回目标和下一阶段依赖。
- 后端必须对齐 [阶段产物合同](stage-artifact-contract.md)，避免 markdown 自由文本二次解析。

## 生产阶段

### 1. 产品定位

目标：明确产品为谁解决什么问题，以及它和普通写作工具、单轮 AI 写作、传统工作流编排工具的区别。

当前定位：

- Yotsuba Ink 是面向小说创作的多阶段生产工作台。
- 核心不是单次生成正文，而是把信息推荐、梗概、大纲、细纲、正文、封面、导出串成可观察、可干预、可写回的创作链路。
- 用户可以按投入程度选择三档模式：
  - 极速生产：轻便、自动、一页 cockpit 跑完。
  - 平衡创作：只在人设/世界观信息阶段人工确认，之后自动生产。
  - 精细定稿：每个阶段都可人工干预、换稿、确认后再继续。

完成标准：

- 产品主线能用一句话讲清。
- 三档模式的用户差异、控制权差异和成本差异清楚。
- 不再把“更多按钮/更多面板”误认为产品能力。

### 2. 需求分析

目标：把用户想看的“流程是否丝滑、语义是否正确、加载是否清晰”拆成可验收需求。

当前需求主线：

- 前端先模拟完整链路，便于逐阶段验收体验。
- Info 阶段使用专属全局加载动画。
- Summary / Outline / Detail / Text / Cover / Export 使用局部流式、局部加载和阶段内反馈。
- 精细模式所有创作阶段必须生成完成后才允许换稿或确认定稿。
- 确认定稿后，编辑入口转为预览态；输入不可编辑，底部保存按钮隐藏。
- 右侧 Wiki、质量、人物关系、世界观为观察与写回系统，不抢占主工作区。
- 创作历史要能一眼看出模式、阶段、状态和产物缩略信息。

完成标准：

- 每个阶段都有明确的用户任务和下一步决策。
- 每个弹窗、面板和候选态都有明确写回对象。
- 没有只为填空间存在的模块。

### 3. 技术选型与架构

目标：确定前后端边界、状态机、事件流和产物合同。

当前选型：

- 前端：React + TypeScript + Vite。
- 后端：FastAPI adapter + domain packages。
- 运行通道：SSE 事件驱动。
- 真实运行阶段：前端通过 `/api/runs/stream` 消费后端 SSE，生产链路不再使用前端 mock stream。
- 动画：以 CSS / motion-react 为主，不引入重型动画依赖。

当前架构边界：

- `apps/web/src/features/pipeline/running/`：运行态阶段页面和运行诊断。
- `apps/web/src/features/pipeline/layout/`：顶部控制、历史、全局壳层。
- `apps/web/src/features/pipeline/state/`：应用状态、真实 SSE 事件归并。
- `apps/web/src/features/pipeline/contracts/`：前端类型合同。
- `docs/architecture/stage-artifact-contract.md`：后端和模型必须对齐的阶段产物合同。

完成标准：

- 前端状态来自统一事件归并，不允许页面各算各的。
- 后端 API 只做适配，编排和质量逻辑进入 domain 层。
- 任何阶段 UI 改动先检查产物合同。

### 4. UI / UX 设计

目标：形成专业的生产工作台体验，而不是 AI 模板页面。

当前设计原则：

- 工作台优先：主内容区承载阶段产物，右侧承载观察系统，底部只承载当前决策。
- 避免 card 堆叠、无意义边框、混乱线条、过重渐变和 hover 上移。
- 所有模式使用统一布局骨架，只切换主题 token 和控制语义。
- 所有全局编辑弹窗居中、有遮罩；右侧观察详情面板无遮罩，避免干扰主内容。
- 所有长内容隐藏滚动条但保留滚动能力。
- 重点内容和辅助日志要有层级区分：主任务 agent、子任务 agent、质量/Wiki 辅助事件、阶段结算不能混成同一种样式。

当前设计经验已沉淀到技能和页面实现：

- Summary：左侧完整梗概，右侧结构节拍、关键转折、人物关系深化。
- Outline：分卷工作台、卷纲详情、角色承接、世界观承接、伏笔账本拆分。
- Detail：章节施工操作台、章节详情、事实/伏笔/关系写回按章节联动。
- Cover：封面阶段独立设计，不套文本阶段模板。
- Export：专业导出工作台，人工操作生成预览和返回工作台。

完成标准：

- 1280 / 1440 / 1728 宽度下无横向滚动、无遮挡、无明显布局跳动。
- 按钮宽高比例稳定，不因状态变化挤压。
- 模式主题色贯穿按钮、弹窗、节点、hover、候选和右侧面板。

### 5. 前端开发与体验验收

目标：保持已经验收过的前端体验稳定，并让真实后端事件无感驱动同一套 UI。

当前状态：基本收口，进入真实后端联调。

已形成的前端链路：

- 极速生产：默认 cockpit，启动后一页自动跑完整链路，不暂停、不跳页。
- 平衡创作：配置启动后进入 Info，确认后进入 cockpit 自动跑后续；版本对比只在用户主动开启并点击时触发。
- 精细定稿：每个阶段进入详情页，局部流式生成，完成后换稿/确认，确认后绿色继续进入下一阶段。

当前前端验收重点：

- Info 换一版有专属 loading，确认后底部决策区丝滑收起。
- Summary / Outline / Detail 弹窗与页面结构保持模式主题一致。
- 所有确认后弹窗转只读预览。
- 右侧人物关系、世界观、质量、Wiki 详情面板自适应展示，不遮挡主内容。
- Export 不自动跳回 planning；精细模式下由用户人工导出并返回工作台。
- 创作历史按模式展示背景、阶段进度、产物缩略和操作入口。

完成标准：

- 真实后端 SSE 链路完整可走通。
- 控制台无业务 error/warn。
- 用户可以逐阶段判断“语义是否正确、过渡是否丝滑、加载是否清晰”。
- 前端产物字段与后端阶段合同一致。

### 6. 后端开发

目标：用 FastAPI domain runner、真实 Provider、结构化产物校验和持久化状态替换 mock 运行。

后端阶段暂不展开实现，后续应按以下顺序推进：

- 对齐阶段产物合同和 prompt 输出 schema。
- 建立 run / stage / artifact / writeback 的持久化模型。
- 已实现真实 SSE 事件流，继续保持前端事件语义稳定。
- 接入知识库、Wiki、质量阀门、人物关系网、世界观写回。
- 实现三档模式的成本、确认点、自动化程度差异。

完成标准：

- 后端直接返回结构化 artifact，不要求前端从自由文本清洗字段。
- mock 事件和真实 SSE 事件可平滑替换。
- 每个阶段有失败、重试、取消、恢复策略。
- 生产代码不再提供 mock provider；测试 fake provider 只允许存在于 `tests/`。
- 各阶段输出长度通过 `generation_budget` 持久化配置，并进入 prompt 构造。

### 7. 前后端协调

目标：让前端体验合同和后端工程合同闭环。

协调原则：

- 前端已有的阶段 UI 不反向逼迫后端返回难解析的大段文本。
- 后端 Prompt / Context / Loop 需要围绕稳定小字段设计。
- 用户编辑、候选选择、确认定稿都必须写成明确事件。
- Story Bible、Wiki、人物关系网、世界观、质量阀门要有阶段来源标记。

完成标准：

- 每个前端操作都有后端事件或 mutation 对应。
- 每个后端事件都有前端消费位置和用户可见反馈。
- 双端不重复维护两套阶段状态机。

### 8. 测试与验收

目标：从体验、合同、状态机和工程质量四层验收。

测试层级：

- 静态构建：`cd apps/web && npm run build`
- 后端回归：`.venv/bin/python -m pytest tests/test_workflow_runner.py -q`
- 浏览器验收：三档模式、阶段跳转、弹窗、候选、确认、导出、历史。
- 合同验收：阶段 artifact 字段、SSE 事件语义、写回目标。
- 视觉验收：无 card 堆叠、无遮挡、无错位、无模式色漂移。

完成标准：

- 前端和后端测试通过。
- 关键路径有浏览器验证截图或明确验收记录。
- 每次回归能快速定位是体验问题、状态问题、合同问题还是后端执行问题。

### 9. 运维部署

目标：把产品从本地验证推进到可持续运行。

后续部署阶段应覆盖：

- 前端构建与静态托管。
- 后端 API 服务部署。
- 模型 provider 配置和密钥管理。
- 运行时资源、默认 prompt、workflow template 发布。
- 本地 run 数据和生产持久化策略区分。
- 日志、指标、失败告警和成本监控。

完成标准：

- 测试 fake、开发真实 provider、生产 provider 有清晰差异。
- 密钥和用户数据不进入源码。
- 运行失败可追踪、可恢复、可解释。

## 持续更新规则

每次出现以下变化，都要更新本文档或其关联文档：

- 产品阶段变化，例如从前端体验验收进入真实 API 后端编排。
- 三档模式语义变化。
- 阶段产物字段、SSE 事件、写回目标变化。
- UI 工作台布局、弹窗体系、候选/对比逻辑形成新的稳定模式。
- 后端 Prompt / Context / Loop 工程进入实现。
- 测试、部署、运维策略落地。

更新方式：

- 本文档记录生产模式、阶段状态和跨阶段决策。
- [stage-artifact-contract.md](stage-artifact-contract.md) 记录阶段产物和模型返回合同。
- [frontend-workbench.md](frontend-workbench.md) 记录前端工作台结构。
- 后续如后端编排稳定，再更新 [backend-pipeline.md](backend-pipeline.md)。
